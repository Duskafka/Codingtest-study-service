## 한 줄 요약

<!-- AI 초안: 자기 말로 다시 쓰기 -->
JWT 대신 Spring Session JDBC (세션을 Supabase DB에 저장)를 골랐다. 클라이언트가 같은 출처의 SPA 하나뿐이라 JWT의 장점을 쓸 곳이 없고, 탈퇴나 탈취 때 바로 끊을 수 있어야 하기 때문이다. 대신
요청마다 세션 조회 쿼리가 생기는 것을 감수했다.

## 배경

<!-- AI 초안: 자기 말로 다시 쓰기 -->

- GitHub로 로그인한 뒤 로그인 상태를 어떻게 유지할지 정해야 한다. 로그인 PR (P1 1주) 전에 정해야 의존성과 보안 설정이 정해진다.
- ADR-001의 '배경'에는 JWT와 Redis가 적혀 있었고, 계획 D22에는 Spring Session JDBC가 적혀 있었다. 둘 중 하나로 맞춰야 한다.
- 이 프로젝트의 조건
    - 클라이언트: Nginx가 같은 도메인에서 SPA (PWA)와 `/api/*`를 함께 서빙한다 (4.1). 모바일 네이티브 앱은 만들지 않는다 (2.4).
    - 로그인: Spring Security OAuth2 Client로 GitHub 로그인 (4.5). GitHub access token은 신원 확인에만 쓰고 저장하지 않는다.
    - 권한: 멤버·방장 검사는 `StudyAccess`가 요청마다 DB의 멤버십으로 한다 (4.5, IDOR 방지).
    - 탈퇴·계정 삭제 (5.16)를 하면 그 사용자의 로그인이 바로 끊겨야 한다.
    - 배포로 컨테이너가 바뀌어도 로그아웃되면 안 된다 (D22).
    - 서버 1대, DB는 Supabase 무료, 비용 상한 월 $15 (9.3).

## 선택지

### A. Spring Session JDBC (세션 ID 쿠키 + DB 저장)

#### 장점

1. Spring Security `oauth2Login`의 기본 동작 그대로 쓴다. 로그인 성공 처리를 따로 만들지 않는다.
2. 세션 행을 지우면 바로 로그아웃된다. 탈퇴, 탈취 대응, '모든 기기에서 로그아웃'이 쉽다.
3. 세션 ID는 HttpOnly 쿠키에 있어서 JS가 읽을 수 없다. XSS가 나도 토큰 자체를 빼 가지는 못한다.
4. 이미 쓰는 Supabase DB에 저장하니 인프라와 비용이 늘지 않는다. 배포로 컨테이너가 바뀌어도 세션이 남는다.

#### 단점

1. 요청마다 세션 조회와 마지막 접근 시각 갱신 쿼리가 생긴다. Supabase 커넥션 풀 (최대 5~10, 9.4)을 같이 쓴다.
2. 쿠키 기반이라 CSRF 대응이 필요하다. Spring Security의 SPA용 CSRF 설정을 정확히 따라야 한다 (4.5).

### B. JWT (access token + refresh token)

#### 장점

1. 서버가 토큰 서명만 확인하면 돼서 세션 저장소 조회가 없다.
2. 여러 도메인, 네이티브 앱, 서비스 간 호출에서 토큰을 그대로 넘길 수 있다.
3. 채용 공고와 자료에서 자주 보이는 방식이다.

#### 단점

1. 이 프로젝트에서는 장점 2를 쓸 곳이 없다. 클라이언트는 같은 출처의 SPA 하나뿐이다.
2. 장점 1도 사라진다. `StudyAccess`가 어차피 요청마다 DB에서 멤버십을 확인한다.
3. 만료 전에 무효화하려면 차단 목록 저장소가 필요하다. 결국 서버에 상태가 생기고, 보통 Redis를 붙인다.
4. 토큰을 localStorage에 두면 XSS로 빼 갈 수 있다. HttpOnly 쿠키에 두면 CSRF 대응이 다시 필요해서 A와 다르지 않다.
5. OAuth2 로그인 성공 뒤 토큰 발급, refresh 토큰 저장·회전, 재발급 API를 직접 만들어야 한다.
6. Redis를 쓰면 2GB 서버의 메모리를 나눠 쓰거나 외부 서비스를 하나 더 관리해야 한다.

### 제외한 선택지

- 서버 메모리 세션 (Spring 기본): 배포로 컨테이너가 바뀌면 모두 로그아웃된다 (D22 위반).
- Spring Session Redis: 세션은 DB로 충분하다. Redis만을 위해 인프라를 늘릴 이유가 없다. 스케줄러 잠금은 ShedLock JDBC, 요청 수 제한은 서버 1대라 메모리 (Bucket4j)로 한다.

## 결정

<!-- AI 초안: 자기 말로 다시 쓰기 -->

- 결정: Spring Session JDBC로 로그인 상태를 유지한다. JWT와 Redis는 쓰지 않는다.
- 결정을 가른 이유: JWT의 장점 (무상태, 여러 클라이언트)이 이 프로젝트의 조건 (같은 출처 SPA 하나, 요청마다 DB 권한 검사)에서는 생기지 않는다. 반면 단점 (즉시 무효화가 어려움, 토큰 보관 위험,
  직접 만들 코드)은 그대로 남는다.
- 세션 설정
    - 쿠키: HttpOnly, Secure, SameSite=Lax
    - 만료: 30일 롤링 (마지막 요청부터 30일). 길수록 편하지만 쿠키를 탈취당했을 때 쓸 수 있는 기간도 길어진다. 탈퇴·로그아웃 시 세션 행 삭제로 보완한다.
    - CSRF: 토큰을 쿠키로 내려주고, SPA가 `X-XSRF-TOKEN` 헤더로 돌려보낸다. Spring Security 6.4부터 있는 SPA용 설정 (`csrf.spa()`)을 쓸 수 있는지 로그인 PR에서 공식 문서로 확인한다.
    - 웹훅 경로 (`/webhooks/**`)는 세션과 CSRF에서 빼고 서명으로만 인증한다.
- 스키마: Spring Session 기본 테이블을 Flyway 마이그레이션으로 만든다 (`spring.session.jdbc.initialize-schema: never`).

### 결정 전: 로그인에 쓸 GitHub 앱 종류 (4.6)

<!-- 아직 정하지 않음. 로그인 PR 전에 정한다. -->

- OAuth App을 로그인용으로 따로 둔다 / GitHub App의 사용자 인증으로 로그인한다.
- 판단할 것: 앱을 하나로 줄일 수 있는지, 로그인 동의 화면에 보이는 권한, Setup URL의 `installation_id` 위조 대응 (5.2)과 관계.

## 감수하는 것

<!-- AI 초안: 자기 말로 다시 쓰기 -->

1. 요청마다 생기는 세션 쿼리
    - 실제 문제가 되는 조건: 세션 쿼리 때문에 커넥션 풀이 모자라거나 API 응답 시간이 눈에 띄게 늘 때.
    - 대응: 운영하면서 커넥션 풀 사용량과 응답 시간을 측정한다 (9.4, 9.9).
2. "JWT를 왜 안 썼나요?"에 답할 준비
    - 많이 쓰는 방식을 고르지 않았으니, 이 ADR의 조건과 이유로 설명한다.
